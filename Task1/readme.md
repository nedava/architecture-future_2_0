### Миграция ESB Apache Camel на DataMesh архитектуру

- Транспорт: Camel (JMS, HTTP, MQ) -> Apache Kafka
- Интеграции: Camel components (file, jdbc, soap, rest) -> Kafka Connect/domain adapters
- ФЛК: Camel processors, XSD ->
  - структурный контроль: с помощью Schema Registry, проверка формата на входе в Kafka
  - логический контроль: на уровне Spark-обработчиков
- ETL: Camel -> Apache Spark (Batch ETL / Structured Streaming ETL)
- Маршрутизация: Camel routes -> Kafka topics
- Оркестрация: Camel timers, sequencing, retries -> Apache Airflow

#### Переходный период по этапам

1. ESB → Kafka (bridge). Camel остаётся, Kafka — новый транспорт, ETL в Camel
2. Вынос ETL из ESB. Camel теряет трансформации, Spark начинает выполнять ETL, ФЛК переносится в Spark
3. Camel остаётся только как legacy adapter, protocol bridge
4. Полный отказ от ESB. Kafka Connect/adapters, Spark ETL, Airflow-оркестрация


## Анализ проблемных мест и их приоритизация

### Must

#### Монолитный DWH

Отсутствие горизонтального масштабирования у SQL Server 2008. Конкурентность запросов за ресурсы при
большом объеме данных, все преобразования в рамках одной системы.

Для данной проблемы свойственны следующие бизнес-сценарии: значимая задержка при формировании отчетов для руководителей
в своих зонах ответственности для управления и мониторинга операционной деятельности. Например, принятие решений
финансовым директором вынуждено откладывается на несколько часов, руководитель клиники не способен оперативно отслеживать
операционную деятельность. Последствиями могут стать упущенная выручка и невозможность оперативного реагирования на
изменения рынка.

Цель бизнеса: увеличение выручки.

#### Смешанный тип нагрузки для DWH

DWH работает в режиме OLTP и OLAP для PowerBuilder и Power BI соответственно. При возникновении нагрузки в часы-пик
скорость формирования отчетов сильно проседает из-за операционной деятельности, и наоборот, формирование тяжеловесных 
отчетов при повышенной аналитической нагрузке скажется на операционной деятельности.

От этого страдают, например, сценарии записи пациента к врачу, его приема специалистом, обработка платежей. Это скажется
на снижении лояльности клиентов как следствие падения качества услуг.

Цель бизнеса: снижение рисков.


### Should

#### Повышенный показатель time to market

Одним из основных недостатков монолитного DWH можно выделить увеличенное время доставки фичей в продуктивную среду, 
так как любое новое направление или продукт потребуют изменений в монолитном решении, что требует больше времени и ресурсов,
нежели в подходе Data Mesh, при этом увеличивается сложность тестирования из-за взаимозависимостей.

Данная проблема может повлечь следующие возможные бизнес-сценарии: запуск нового финтех-продукта на несколько месяцев
задерживается; компания-конкурент выпускает новый функционал страхования быстрее на несколько месяцев. К последствиям
можно отнести снижение конкурентоспособности и потеря возможностей.

Цель бизнеса: ускорение выхода на рынок.

#### Отсутствие согласованности в кросс-доменных метриках

Разные отделы компании могут вычислять одни и те же метрики по-разному, так как нет согласованного семантического слоя.

К страдающим при этом бизнес-сценариям можно отнести: получение неоднозначной управленческой отчетности дирекцией
компании (разные отчеты отображают разные цифры по одним и тем же метрикам); маркетинг не получает достоверной информации
о наиболее эффективных каналах продаж. Последствием тому могут явиться ошибки в принятии стратегических решений.

Цель бизнеса: ускорение выхода на рынок.


### Could

#### Отсутствие гибкости при построении аналитики

Для кастомизации создаваемых отчетов, рядовые сотрудники вынуждены прибегать к помощи специалистов BI-системы, а они,
в свою очередь, являются узким горлышком в плане ресурсов компании.

Примером такой проблемы может быть чрезмерно длительное формирование маркетинговых отчетов маркетологами, руководитель не
может построить самостоятельно отчет по загруженности сотрудников. Все это является причиной неэффективного использования
ресурсов компании.

Цель бизнеса: оптимизация затрат.

#### Риски для информационной безопасности

Хранение разнотипных данных вместе в одной БД с учетом сложности разграничения доступа и устаревшей системой способствует
увеличению уровня риска для информационной безопасности. 

Бизнес-сценариями могут явиться: утечка данных, нарушения,
выявленные в процессе аудита регулятором. Данные сценарии могут иметь последствия в виде больших штрафов и репутационных
потерь.

Цель бизнеса: снижение рисков.


### Won't

Повышенная сложность эксплуатации. Поддержка старого решения и возможный дефицит специалистов в этой области может
способствовать высоким операционным расходам и рискам, связанным с увольнением ключевых сотрудников.

Цель бизнеса: оптимизация затрат.
